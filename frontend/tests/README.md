# Характеризаційні тести frontend

Тести фіксують **поточну** поведінку Kendr `v0`, зокрема помилкову (ADR-005). Вони пишуться до реструктуризації й мають залишатися зеленими в `v1.0`. У `v2.0` тести з маркером `KNOWN-DEFECT` змінюються разом із виправленням дефекту. Тести backend описано в [`../../backend/tests/README.md`](../../backend/tests/README.md).

## Запуск

З кореня репозиторію:

```bash
cd frontend
npm install --legacy-peer-deps                  # без прапорця npm падає з ERESOLVE (D-CFG-03)
npx vitest run tests/unit tests/integration      # однократний запуск
npm test                                         # режим спостереження (watch)
```

Тести e2e (`tests/e2e`, Playwright) потребують запущених застосунку й БД і сюди не входять.

Покриття (пакет `@vitest/coverage-v8` не входить до `package.json`, ставиться без збереження; значення виводиться тими самими параметрами, що й заміри `v0` у `tools/measure.mjs`):

```bash
npm i --no-save --legacy-peer-deps @vitest/coverage-v8@<версія vitest>
npx vitest run tests/unit tests/integration --coverage.enabled --coverage.provider=v8 --coverage.reportOnFailure=true "--coverage.include=src/**/*.{js,jsx}" --coverage.reporter=text --coverage.reporter=json-summary
```

## Склад

| Каталог | Що там лежить |
|---|---|
| `unit/` | чисті функції без DOM: експорт сайту, посилання, операції над деревом блоків, конфігурація редактора, реєстр блоків |
| `integration/` | компоненти й контексти React (Testing Library, jsdom) |
| `fixtures/` | вхідні дані для золотих тестів |
| `golden/` | «золоті» файли: повний вивід функції на `v0`; `all-blocks.html` і `editor-defaults.html` свідомо перегенеровано у `v2.0` (D-SEC-27, D-BLK-06) |
| `helpers/` | заглушки блоків і панелей (`stubs.jsx`), заглушки модальних вікон і дочірніх компонентів магазину (`shopStubs.jsx`), порівняння із золотим файлом (`golden.js`), підміна JSZip (`fakeZip.js`), заглушки віджета Turnstile й важких компонентів сторінки входу (`authStubs.jsx`) |

## Як це працює

- **Золоті файли.** `expectGolden(actual, 'export/…html')` порівнює вивід з файлом у `golden/` (переноси рядків `CRLF` і `LF` не розрізняються). Якщо вивід змінився, тест називає перший рядок, що розійшовся. Свідоме оновлення (лише разом із зміною поведінки): `UPDATE_GOLDEN=1 npx vitest run tests/unit` (у PowerShell: `$env:UPDATE_GOLDEN=1; npx vitest run tests/unit; Remove-Item Env:UPDATE_GOLDEN`). Рік у футері не потрапляє в золоті файли: сторінки мають власний текст футера, а для блока за замовчуванням `copyright` у тесті закріплено (`exportDefaults.test.jsx`).
- **Реєстр блоків.** Компоненти блоків і панелей налаштувань підмінено заглушками (`helpers/stubs.jsx`) через `vi.mock`: тест перевіряє, який саме компонент вибирає `BlockRenderer` і `SettingsTab` для кожного типу, а що отримує компонент — через props, записані заглушкою. Таблиця «тип → компонент» тепер береться з дескрипторів `core/blockRegistry.js` (v1.0, ADR-002), і ці тести підтверджують, що відповідність не змінилась. Панелі налаштувань завантажуються лінивим `import()`, тому `SettingsTab.test.jsx` чекає на них асинхронно (`findBy*`).
- **Дескриптори.** `unit/blockRegistry.test.js` перевіряє сам реєстр: повноту дескрипторів усіх 15 типів, наявність файлів для всіх лінивих імпортів, відповідність каталогу `blocks/` реєстру, псевдоніми (різні для рендера, налаштувань і експорту, як у `v0`), значення за замовчуванням і `toHtml` каталогу та вітрини.
- **Глобальні блоки.** `unit/globalBlocks.test.js` фіксує нормалізацію шапки й підвалу (`normalizeGlobalBlocks`, `resolveGlobalData`) і окремий варіант попереднього перегляду (`mergeGlobalBlocks`: дані блока, формати даних сайту «масив» і «об'єкт із ключем 0», запасні значення). Правила збігаються з чотирма копіями з `v0` (перевірено порівнянням на 80 000 випадкових наборах даних); `unit/globalBlockTypes.test.js` описує предикати типів і таблицю псевдонімів.
- **Порівняння props.** `unit/blockProps.test.js` перевіряє `areBlockPropsEqual`, спільний компаратор `React.memo` для одинадцяти блоків (структурне порівняння даних замість `JSON.stringify`).
- **Вкладені макети.** `integration/BlockNesting.test.jsx` перевіряє, що `LayoutBlock` отримує рендерер дочірніх блоків із контексту (`BlockRendererContext` у режимі перегляду, `EditableBlockContext` у режимі редактора), а не імпортує його: реальні `BlockRenderer` і `LayoutBlock`, листові блоки замінено заглушками.
- **Цикли імпорту.** `unit/importCycles.test.js` будує граф імпортів `src` (статичних і динамічних) і вимагає, щоб циклів не було; тест замінює ручний запуск `madge --circular`. Тести цього розділу охороняють результат реструктуризації `v1.0` (D-BLK-03, D-BLK-04, D-DUP-07), а не відтворюють дефекти `v0`, тому в таблиці покриття дефектів їх немає.
- **Експорт.** `siteExporter.test.js` підміняє мережу (`fetch`), `JSZip` і `file-saver`; `htmlGenerator` працює справжній, тож перевіряється весь шлях від сторінок до файлів архіву. `unit/exportHtml.test.js` перевіряє допоміжні функції підстановки значень у HTML (`escapeHTML`, `transformLink`, `cssNumber`, `getPaddingStyle`, `renderButtonHTML`; D-SEC-27).
- **Контракт із сервером.** `unit/blockTypesContract.test.js` порівнює типи реєстру блоків із `backend/config/blockTypes.js`, який сервер використовує для перевірки `block_content` (D-BLK-05): новий блок без рядка в цьому переліку не збережеться на сервері.
- **Кошик.** `CartContext.test.jsx` перевіряє, що саме кошик запам'ятовує в `localStorage` (рядок з уже обчисленою ціною), а не ціноутворення сервера (D-BIZ-01), а також що оновлення не змінює попередній стан на місці і не дублюється в `StrictMode` (D-ARC-13).
- **Навігація.** `unit/routeTargets.test.js` читає маршрути з `app/App.jsx` і перевіряє, що кожен статичний перехід у коді (`navigate('/…')`, `<Link to="/…">`, `<Navigate to="/…">`) веде на оголошену адресу (D-CON-02). Тест працює над текстом коду, тому нова помилка в адресі переходу не потрапить у збірку непоміченою.
- **Вхід за запрошенням.** `integration/InviteRedirect.test.jsx` проходить шлях `/invite/<токен>` → вхід → (перемикання «вхід ↔ реєстрація») → запрошення зі справжньою маршрутизацією: справжні `InvitePage` і `AuthPage`, замінені лише мережа (`apiClient`), віджет Turnstile та важкі дочірні компоненти (D-CON-03).
- **Оплата.** `integration/PaymentMethodModal.test.jsx` перевіряє, що вікно пропонує лише картку LiqPay, і що в коді застосунку не лишилось ні кнопки, ні конфігурації, ні викликів маршрутів Google Pay (ADR-006).
- **Допоміжні функції сайтів.** `unit/siteUtils.test.js`: лічильник власних сайтів (не враховує сайти співавтора), ознака «глядач» (режим лише перегляду в панелі керування) і правило показу розділу «Шаблони». `unit/mediaUtils.test.js`: адреса вкладень тікета береться зі змінної `VITE_API_URL` (D-CON-04); модулі скидаються й імпортуються наново для кожного значення змінної.
- **Ціна на клієнті.** Ціну в інтерфейсі магазину обчислюють три місця: `ProductCard` (знижка товару), `ProductDetailPage` (знижка варіанта, товару чи категорії + надбавки варіантів) і `CartPage` (сума збережених цін). Тести `ProductCard.test.jsx`, `ProductDetailPage.test.jsx`, `CartPage.test.jsx` фіксують кожне правило окремо, а також те, що йде в кошик (`priceInfo`) і в запит оформлення (лише `id`, `quantity`, `options` — без ціни, її сервер бере з БД).

## Маркер `KNOWN-DEFECT`

Назва тесту, що фіксує помилкову поведінку з реєстру дефектів ([`docs/02-analysis/defects.md`](../../docs/02-analysis/defects.md)), містить `KNOWN-DEFECT D-xx`. Усі такі тести зелені на `v0`. При виправленні очікування змінюється на правильне, а маркер видаляється. Станом на крок 7.6b маркерів у тестах frontend не лишилось: усі тести з `KNOWN-DEFECT` перевернуто.

## Покриття дефектів

| Дефект | Файл | Що фіксується |
|---|---|---|
| D-SEC-27 | `unit/htmlGenerator.test.js`, `unit/exportHtml.test.js` | експорт екранує `<`, `>`, `&` і лапки в текстах, `<title>`, описі, посиланнях (`transformLink` повертає значення, придатне для `href="…"`); числові значення в `style` проходять `cssNumber` і не можуть закрити атрибут (виправлено в v2.0, крок 7.5) |
| D-BLK-06 | `unit/htmlGenerator.test.js`, `unit/exportDefaults.test.jsx`, `unit/blockRegistry.test.js`, `unit/siteExporter.test.js` | блоки `global-header` і `global-footer` потрапляють в експорт: блоки сторінки з порожнім `data` беруть дані з налаштувань сайту (масив блоків, об'єкт-блок, об'єкт даних, рядок JSON), дубля шапки немає, підвал виводить `copyright` і посилання (виправлено в v2.0, крок 7.5) |
| D-SEC-11 | `integration/FooterBlock.test.jsx` | посилання підвалу й соцмереж проходять `resolveSiteLink`: відносні отримують префікс сайту, `javascript:`, `data:`, `vbscript:` і порожні дають `#` (виправлено в v2.0, крок 7.5) |
| D-BLK-05 | `unit/blockTypesContract.test.js` | типи реєстру блоків збігаються з `backend/config/blockTypes.js` (серверна частина — у README backend) |
| D-BLK-07 | `unit/blockUtils.test.js` | `moveBlock` і `handleDrop` коригують шлях призначення після видалення з того самого списку: блок, перенесений зі списку в контейнер нижче, потрапляє саме туди, куди його кинули (два макети, середина списку, глибоке вкладення, інша колонка), а перенесення блока всередину самого себе нічого не змінює (виправлено в v2.0, крок 7.6b) |
| D-ARC-13 | `integration/CartContext.test.jsx` | `addToCart` не змінює об'єкт попереднього стану, інші позиції зберігають ідентичність, кілька додавань в одному `act` дають правильну кількість, у `StrictMode` позиція додається один раз і пишеться в `localStorage` один раз, збій `setItem` не ламає кошик (виправлено в v2.0, крок 7.6b) |
| D-CON-02 | `unit/routeTargets.test.js` | вихід із профілю й перехід із заблокованого сайту ведуть на `/login` і `/my-sites`, а не на адреси без маршруту `/auth` і `/dashboard`; будь-який новий перехід на адресу, якої немає в `App.jsx`, провалює тест (виправлено в v2.0, крок 7.6b) |
| D-CON-03 | `integration/InviteRedirect.test.jsx` | гість із запрошення після входу повертається до `/invite/<токен>` і приймає запрошення з тим самим токеном; адреса повернення переживає перемикання «вхід ↔ реєстрація» (виправлено в v2.0, крок 7.6b) |
| D-CON-04 | `unit/mediaUtils.test.js` | адреса вкладень і аватарів у зверненні будується від `VITE_API_URL` (із запасним `http://localhost:5000`), а не від зашитого значення; `javascript:` і `vbscript:` відкидаються (виправлено в v2.0, крок 7.6b) |
| ADR-006 | `integration/PaymentMethodModal.test.jsx` | вікно способу оплати пропонує лише LiqPay; у коді немає Google Pay (кнопки, конфігурації, викликів `/pay/gpay` і `/upgrade/gpay`) |
| D-BIZ-01 | `integration/ProductCard.test.jsx`, `integration/ProductDetailPage.test.jsx`, `integration/CartPage.test.jsx` | клієнт показує ціну трьома окремими обчисленнями: картка враховує знижку товару або найбільшу знижку категорій, але не надбавки варіантів; сторінка товару бере першу знайдену знижку (варіант → товар → категорія), а не найбільшу; кошик показує збережену ціну. На сервер іде лише `id`, `quantity` і `options`, ціну позиції сервер рахує сам (виправлено в v2.0, крок 7.3; картка оновлена тоді ж) |
| D-BLK-01 | `integration/BlockRenderer.test.jsx`, `integration/SettingsTab.test.jsx`, `unit/editorConfig.test.jsx`, `unit/blockRegistry.test.js` | таблиці «тип → компонент», «тип → панель» і значення за замовчуванням, розкидані по різних файлах (3 з 6 місць); різний набір псевдонімів (`footer` є в налаштуваннях, немає в `BlockRenderer`) |
| D-BLK-02 | `unit/htmlGenerator.test.js`, `unit/exportDefaults.test.jsx`, золоті файли | експорт — другий рендерер: окремі правила для кожного блока, заглушки каталогу й вітрини |

Окремо зафіксовано особливості без номера в реєстрі (позначені в назвах словом «особливість»): `text-align: undefined` у «Перевагах», нульовий відступ блока стає 60 px, `overlay_opacity = 0` стає 0.5, поля `style` і `sizePreset`, які записує редактор і не читає експорт, приймання `.ico` як `.jpg`, завантаження будь-якого значення ключа `url`/`href` як медіафайлу.
