# Результати замірів

Тут лежать метрики версій, виміряні тими самими інструментами, що й вихідна версія (`v0`). Інструменти й параметри описано в [`tools/README.md`](../../tools/README.md).

| Теґ | Що містить | Метрики |
|-----|------------|---------|
| `v0` | вихідний код | [`../02-analysis/metrics-before.md`](../02-analysis/metrics-before.md), числа — `../02-analysis/raw/metrics-v0.json` |
| `v0.1-tests` | `v0` + характеризаційні тести (поведінка не змінена) | розділи 10 і 11 у `metrics-before.md` |
| `v1.0` | реструктуризація | `v1.0/metrics.md` |
| `v2.0` | виправлення дефектів | з'явиться після етапу 7 |

## Структура каталогу версії

```text
docs/04-results/<теґ>/
├── metrics.md      таблиці порівняння з v0 (створює tools/summarize.mjs)
├── metrics.json    ті самі числа для наступних порівнянь
└── raw/            сирі виводи інструментів і environment.txt (коміт, версії Node, npm, Python)
```

`metrics.md` і `metrics.json` генеруються, вручну не редагуються. Висновки й тлумачення чисел винесено в окремі файли поруч (`analysis.md`).

## Як порівнювати

Колонка `v0` у таблицях береться з `metrics-v0.json`, тож зміна завжди показана відносно вихідної версії. Для `v2.0` у `summarize.mjs` можна передати кілька файлів через `--baseline`, і таблиці міститимуть колонки `v0`, `v1.0`, `v2.0`.

Показники, які залежать від складу коду, а не від його якості, слід читати з поправкою:

- рядки коду й кількість функцій зростають, коли великі файли розбито на шари (більше файлів, імпортів і оголошень);
- покриття backend рахується за переліком файлів із `backend/vitest.config.mjs`; після `v0.1` у перелік додано `repositories/` і `services/`, тому знаменник покриття `v1.0` більший, ніж у `v0.1`;
- кількість ендпоінтів і розподіл доступу мають лишатися незмінними до `v2.0`: реструктуризація не змінює зовнішню поведінку (виняток `v1.0` — видалено один недосяжний ендпоінт, D-DEAD-01).
