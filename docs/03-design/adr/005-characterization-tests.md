# ADR-005: Характеризаційні тести перед рефакторингом

- Статус: запропоновано
- Дата: 11.10.2026
- Версія: між `v0` і `v1.0`
- Пов'язані дефекти: D-TST-01 (немає тестів backend), D-TST-02 (застосунок не експортується)

## Контекст
Тестовий код — 126 рядків у трьох файлах (один unit, один інтеграційний, один e2e), усі на frontend, що становить 0,30 % від продуктового коду. Backend тестами не покритий. Без тестів неможливо довести, що реструктуризація (`v1.0`) не змінила поведінку.

## Рішення
Перед будь-яким рефакторингом написати тести, що фіксують **поточну** поведінку, у тому числі помилкову. Тест відомого дефекту маркується коментарем `// KNOWN-DEFECT D-xx` (наприклад, `// KNOWN-DEFECT D-SEC-03`); у `v2.0` його очікування змінюється разом із виправленням. Порядок відтворення дефектів — `docs/02-analysis/defects.md`, розділ «Пріоритет відтворення тестами».

Пріоритет за ризиком:
1. Оформлення замовлення та розрахунок суми, списання залишків (`order`).
2. Контроль доступу до замовлень і ресурсів сайту.
3. Збереження сторінки та експорт сайту (`page`, `site`, `htmlGenerator`).
4. Автентифікація (`auth`).

Інструменти: Vitest на обох сторонах, `supertest` для HTTP-тестів backend, тестова MySQL із `db/schema.sql` (окремий сервіс у `docker-compose.yml`), Testing Library й jsdom для компонентів frontend. Вивід експорту сайту порівнюється із золотими файлами (`frontend/tests/golden/`): повний вивід функції на `v0` зберігається в репозиторії, і будь-яка зміна експорту стає видимою. Компоненти блоків у тестах frontend підмінено заглушками, щоб перевіряти вибір компонента за типом блока, а не їхній вигляд. Існуючий Playwright-тест лишається.

Передумова: у `server.js` виклик `app.listen` стоїть у самому модулі без експорту `app`, тому першою (поведінково нейтральною) правкою є виділення створення застосунку в `app.js`.

```
backend/tests/
├── characterization/   orders, auth, sites, pages
└── helpers/            testDb.js, factories.js
frontend/tests/
├── unit/               htmlGenerator, siteExporter, blockUtils, editorConfig, linkUtils
├── integration/        BlockRenderer, SettingsTab, CartContext, ProductCard, ProductDetailPage, CartPage
├── helpers/            stubs.jsx, shopStubs.jsx, golden.js, fakeZip.js
├── fixtures/ golden/   дані й еталонний вивід експорту
└── e2e/
```

## Розглянуті альтернативи
- Писати тести після рефакторингу: тоді вони підлаштовуються під новий код і нічого не доводять.
- Лише e2e-тести: повільні й не локалізують помилку.

## Наслідки
- Частина тестів фіксує помилкову поведінку, це свідомо і відображено маркерами.
- Потрібна тестова БД; запуск тестів вимагає Docker або локальної MySQL.

## Як перевіряємо
- Усі характеризаційні тести зелені на `v0` до початку рефакторингу.
- Покриття (v8 / c8) і кількість тестів до/після заносяться в таблицю метрик.
