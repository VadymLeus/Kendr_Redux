# Характеризаційні тести backend

Тести фіксують **поточну** поведінку Kendr `v0`, зокрема помилкову (ADR-005). Вони пишуться до рефакторингу й мають залишатися зеленими в `v1.0` (реструктуризація не змінює поведінку). У `v2.0` тести з маркером `KNOWN-DEFECT` змінюються разом із виправленням дефекту.

## Запуск

З кореня репозиторію:

```bash
docker compose up -d          # тестова MySQL 8 на порту 3307; дочекайтеся статусу healthy (docker compose ps)
cd backend
npm install --legacy-peer-deps   # без прапорця npm падає з помилкою "edgesOut" (імовірно через react-dnd у залежностях backend, D-DEAD-07)
npm test                      # усі тести
npm test -- app.smoke         # лише один файл
npm run test:coverage         # покриття (v8)
```

Зупинити й видалити тестову БД: `docker compose down -v`.

## Як це працює

- `docker-compose.yml` піднімає окрему MySQL (`127.0.0.1:3307`, база `kendr_test`). Робоча БД розробки (`3306`, `KendrDB`) не використовується.
- `tests/helpers/globalSetup.mjs` перед усіма тестами перестворює базу зі `db/schema.sql` (назва бази підставляється `kendr_test`).
- `tests/helpers/testEnv.mjs` задає змінні середовища тестів і містить захист: `assertTestDatabase` зупиняє тести, якщо вони спрямовані не на `127.0.0.1:3307/kendr_test`.
- Перед кожним тестом `resetDb()` очищає всі таблиці й додає рядок `global_settings`; дані створюють фабрики (`tests/helpers/factories.js`) прямими SQL-запитами.
- Застосунок береться з `backend/app.js` (`app.listen` винесено в `server.js`). Модулі backend завантажуються рідним `require` Node, тож підміна властивості модуля (`emailService.sendDigitalGoodsEmail`) діє на контролери.
- Платіжний шлюз LiqPay емулюється підписом (`tests/helpers/liqpay.js`), листи з цифровими товарами перехоплюються.
- Листи автентифікації (`sendOtpEmail`) і запит перевірки Turnstile перехоплює `tests/helpers/outbound.js`: контролери автентифікації імпортують `sendOtpEmail` деструктуризацією, тож підмінити функцію в модулі неможливо, і замість цього підміняється глобальний `fetch` (ним користуються SDK Resend і `verifyTurnstile`). Одноразовий код тест бере з тексту перехопленого листа; запит до невідомої адреси перериває тест.
- Обмежувачі частоти (`express-rate-limit`) ведуть лічильник у пам'яті процесу за `req.ip`. Застосунок працює з `trust proxy = 1`, тому `tests/helpers/client.js` задає кожному запиту власну адресу заголовком `X-Forwarded-For`; тести самих обмежувачів шлють усі запити з однієї адреси. Ліміти автентифікації закріплено в `testEnv.mjs`, щоб локальний `.env` їх не змінював.
- Тест D-SEC-19 і D-ARC-12 створює файли-мітки в `backend/uploads/avatars/custom/` і `backend/tests/.tmp/` (останній каталог у `.gitignore`); мітки видаляються після тесту.
- Тести виконуються послідовно (`fileParallelism: false`), бо ділять одну БД.
- Node у тестах працює в UTC (`TZ` у `testEnv.mjs`): застосунок порівнює `TIMESTAMP` із `new Date()` (блокування сайту, строк запрошення), а контейнер MySQL працює в UTC, тож без цього результат залежав би від часового поясу комп'ютера. Тест `team.test.js` перевіряє, що пояс UTC діє.
- Глобальні налаштування платформи кешуються на 30 с (`platformGuards.js`): тест, що їх змінює, скидає кеш викликом `clearSettingsCache()`.

## Модульні тести (`tests/unit/`)

З `v1.0` (ADR-003) бізнес-правила виносяться із контролерів у `services/`, а SQL — у `repositories/`. Для нових шарів є два види тестів:

- **Характеризаційні** (`tests/characterization/`) проходять через HTTP до реальної БД і лишаються без змін: вони доводять, що рефакторинг не змінив поведінку маршрутів.
- **Модульні** (`tests/unit/`) перевіряють сервіс у відриві від HTTP і БД: репозиторій і модель підміняються `vi.spyOn` на статичних методах класів, перевіряються коди відмов (`ServiceError`), тексти повідомлень і аргументи, з якими сервіс звертається до репозиторію.

| Файл | Що перевіряє |
|---|---|
| `transaction.test.js` | `config/transaction.js`: порядок `getConnection → begin → work → commit → release`, відкат при помилці, збій відкату не приховує причину, з'єднання завжди повертається в пул; те саме на реальній БД через `pool.withTransaction` |
| `sendServiceError.test.js` | `utils/sendServiceError.js`: `ServiceError` → `res.status(status).json({ message })`, решта помилок → `next(error)` |
| `ProductService.test.js` | `services/ProductService.js`: права доступу, нормалізація полів товару, правила відгуків; фіксує D-DEAD-08, D-SEC-18, D-SEC-06 на рівні сервісу |
| `PageService.test.js` | `services/PageService.js`: права доступу до сторінки, обов'язкові поля, переклад дубля slug у 400, правила видалення (головна й остання сторінка), D-BLK-05 на рівні сервісу |
| `OrderService.test.js` | `services/OrderService.js`: оформлення замовлення (перевірки магазину, ліміт неоплачених, залишок, адреса, цифрові товари), оплата LiqPay і Google Pay, списки замовлень; фіксує D-BIZ-01, D-BIZ-02, D-BIZ-08, D-BIZ-09, D-SEC-02, D-SEC-03, D-SEC-07, D-CFG-01 на рівні сервісу |
| `PricingService.test.js` | `services/PricingService.js`: сума замовлення без знижок і надбавок (D-BIZ-01), поведінка при від'ємній і нечисловій кількості |

Модульні тести теж запускаються командою `npm test` (глобальна підготовка схеми БД спільна для всіх файлів, тож Docker потрібен і для них).

## Маркер `KNOWN-DEFECT`

Назва й коментар тесту, що фіксує помилкову поведінку з реєстру дефектів, містять `KNOWN-DEFECT D-xx`. Усі такі тести зелені на `v0`. При виправленні дефекту очікування змінюється на правильне й маркер видаляється; перелік змін заноситься в `docs/04-results`.

Окрім дефектів, `auth.*.test.js`, `users.*.test.js` і `support.test.js` фіксують правильну поведінку автентифікації (реєстрація, підтвердження пошти, вхід, двофакторний вхід персоналу, відновлення пароля, перевірка токена, вхід через Google), профілю, видалення й відновлення акаунта та звернень до підтримки.

Не покрито: одночасні замовлення (друга частина D-BIZ-02, відсутність `FOR UPDATE`) — недетермінований сценарій, фіксується послідовним перепродажем; завантаження файлів (Cloudinary, потрібен зовнішній сервіс), зокрема вкладення звернень до підтримки (`multipart`) і завантаження аватара файлом; справжній обмін кодом із Google (тестується функція перевірки стратегії passport і `googleCallback` із підставним запитом); фактична доставка листів (перехоплюється запит до Resend).
